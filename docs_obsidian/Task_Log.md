## 2026-09-20 — M6.2: process_minutes populated by the watcher (done)
Outside the original plan (like M6.1): closes the scope gap noticed by inspection during M6.1 (see the entry below and the ADR in [[Architecture]]) — `process_minutes` had its schema and `db.insert_process_minutes` ready since M1 but **0 real rows** despite 73k+ samples in `metrics_raw` (76,650 in this session, checked with `tslow status`), because no milestone after M1 had ever called the insert from the watcher. No new migration: the table and its columns already existed.

- [x] **`monitor.py::ProcessGroupAccumulator`** (new class): hooks into the same periodic flush (~60s) that already runs `rollup_1m`/`rollup_1h`/`record_monitor_health`. On every tick with `dt_s > 0` (the same guard already used for `det.evaluate()`), it groups with `grouping.build_groups` the **same snapshots the detector just filtered** (the watcher's own process excluded, reusing the mutation `Detector.evaluate()` already applies to `tick.snapshots`), then accumulates the detector's own per-group formulas for each group. On flush it keeps only the **10 groups with the highest `cpu_percent_avg`** (`_PROCESS_MINUTES_TOP_N`) and resets the accumulator. See the `process_minutes` section in [[Database_Schema]] for the exact semantics of every column (avg/max/peak: not uniform across columns, on purpose).
- [x] **4 `detector.py` functions made public** (`_group_cpu_percent`→`group_cpu_percent`, `_group_ram_private_mb`→`group_ram_private_mb`, `_group_io_bytes_sec`→`group_io_bytes_sec`, `_group_gpu_percent`→`group_gpu_percent`): renamed only, no behavior change. They were private to the detector, now shared with `monitor.py` — reusing them instead of rewriting the same arithmetic avoided the risk of losing a correctness fix already earned once (e.g. discarding reused PIDs via `create_time`, dividing by `self._cores` for group quotas).
- [x] Test: `tests/test_monitor.py` (+4, synthetic data as CLAUDE.md requires): avg/max/RAM-peak/IO-GPU-average/max-instance-count aggregation across several synthetic ticks of the same group (with a third process appearing only on the second tick, for the max-instance-count case), the 10-highest-by-average-CPU cap across 12 synthetic groups, `dt_s<=0` ignored, and an end-to-end test of `monitor._flush` against a real (not mocked) temp DB that checks the row written into `process_minutes`. **Total suite: 151 tests, all green** (`.venv\Scripts\python -m pytest -q`).

The `metrics_1m`/`metrics_1h` rollups (24h/7d/30d, the **default** range for both `tslow dashboard` and the new `tslow web`) only expose them as `<name>_avg`/`<name>_max`. Result: the installed dashboard showed "n/a" on every indicator and "no data for this range" on the chart for any range other than 1h — verified against the real `data/metrics.db` (520 rows in `metrics_1m` over the last 24h, none shown). The existing tests didn't catch it: `test_dashboard_metric_and_range_keys_do_not_crash` covers 24h but only checks it doesn't crash. Regression covered in `test_analytics.py` and a new `test_dashboard.py` test that seeds only `metrics_1m` (via `db.rollup_1m`) and checks for real values (not "n/a") at 24h.

- [x] `src/tslow/web/api.py`: a read-only FastAPI app, one endpoint per public `analytics.py` function — `GET /api/health`, `/api/metrics?range=`, `/api/top-culprits?range=&limit=`, `/api/decisions/stats?range=`, `/api/incidents?range=&limit=`, `/api/overhead?range=`. - [x] **Bug found while writing the tests, before any real use**: FastAPI runs sync `def` dependencies and the sync endpoint in `anyio`'s threadpool, not guaranteed to be the same thread across a dependency and its endpoint. With `database.connect()`'s defaults (`check_same_thread=True`) this raises `sqlite3.ProgrammingError` on the very first query — it would have hit on every single real request to `tslow web`, not just in tests. Fixed by adding an optional `check_same_thread` parameter to `database.connect()` (default `True`, unchanged for every other caller — CLI, watcher, existing tests), passed `False` only from `web/api.py::get_connection`. Safe because each connection is only ever used by one thread at a time regardless (opened and closed within the same request cycle, never concurrently).

CORS limited to `localhost`/`127.0.0.1` origins (any port), for the future frontend dev server — anyone not on localhost gets nothing anyway given the bind.

### Bugs found live and fixed (M2)
1. **`dwm.exe` (L0) flagged as "not responding"**: during the hung test, `IsHungAppWindow` marked a transient main window of `dwm.exe` for one tick (likely another window's open/close animation). Fix: `detector._check_hung` always excludes L0 processes before opening an incident — never an actionable target. Impossible to catch with synthetic tests alone: needed a real desktop session.
2. **Hung CPU threshold divided by the number of cores**: `_check_hung` computed `cpu_pct` as a percentage of the system's TOTAL capacity (÷8 cores), but the plan's threshold ("≥25% of ONE core") should be compared unscaled, the way Task Manager does per-process. A single-threaded busy loop saturated a whole core (100%) but the (wrong) calculation gave 12.5%, under threshold: never detected. Fix: removed the division by `self._cores` at this specific point (still correct elsewhere, where group shares are compared against system-wide thresholds).
3. **`_LeakTracker`'s window equal to the required minimum duration**: both at 600s (10 min). With a deque dropping samples older than 600s, `duration_s` (computed on the samples that REMAIN) almost never reaches 600s with unevenly-spaced real timestamps — the window drops its oldest sample right as it approaches the threshold. 880 MB allocated over 11 minutes, never detected across two runs. Fix: `_LeakTracker`'s window is now 1.5× the required minimum duration (some slack). The original synthetic test (at exact 60s intervals) never caught this: rewritten with 23s ticks to replicate the real irregularity.
